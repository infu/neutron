# Managed Memory Migrations And Uninstall

[Back to the documentation index](./index.md)

This guide is the app-author workflow for persistent Motoko data. It explains
what belongs in `neutron.json`, what each schema and migration module must
export, how a package supports skipped releases, and how Neutron removes data.

> **Current V1 behavior:** initialization, forward migration, same-app
> consolidation, explicit retirement, and uninstall with live managed roots
> are supported. Destructive changes use staged retirement: actor activation
> first preserves the old value in an inaccessible optional field, the checked
> install commit clears that field in the same update that promotes metadata,
> and a later upgrade physically removes the proven-null field.

## Mental Model

An app owns one or more app-local memory roots. Each root has:

- a current positive integer schema version;
- an immutable Motoko schema module for every supported version;
- zero or more forward migration modules;
- one generated persistent actor field whose physical name includes both the
  owner app id and local memory id.

The app release version and memory version are independent. The top-level app
version is a packed semantic release (`0.1.0` is `100`); memory versions remain
ordinary positive schema integers. A frontend or backend code release must
increase the top-level manifest `version` for user-facing distribution without
changing `memory.<id>.version`. Increase the memory version only when the
persistent schema or its clean-install defaults must change.

Neutron handles a memory root differently in each situation:

| Situation             | What Neutron does                                                            |
| --------------------- | ---------------------------------------------------------------------------- |
| Fresh install         | Calls only the current schema's `init()` function.                           |
| Same memory version   | Restores the existing root without calling `init()` or a migration.          |
| Higher memory version | Selects exactly one migration path from the installed version to the target. |
| Explicit retirement   | Stages the root, clears it atomically at checked commit, then finalizes it.   |
| App uninstall         | Uses the same staged protocol for every live root owned by the removed app.  |

### Commit-atomic retirement

Neutron never omits a live stable field during the one-way `install_code`
step. For each newly retiring root, the migration renames
`NeutronMemoryStore_<scope>` to an inaccessible
`NeutronRetiredMemoryStore_<scope> : ?OldStore` and initializes it with the old
value. `<scope>` is
`a<app-id-length>_<app-id>_r<memory-id-length>_<memory-id>`.
The compiler records one bounded, canonical retirement descriptor in the
stable signature so finalization still knows the exact old schema after an app
has been uninstalled.

The current development baseline writes the owner-scoped
`@neutron-managed-memory-retirements-v2` marker. Development canisters with
another marker shape must be reinstalled.

After `kernel_runtime_info` verifies the activated actor, the generated
compiler callback sets each staged optional to `null` synchronously inside
`kernel_install_commit`. A trap rolls back both the clears and journal
promotion. The next successful compile imports the recorded old schema and
omits only that proven-null retired field. Newly retiring roots receive a new
descriptor; if there are none, the canonical marker records an empty list.

An app uninstall releases its manifest ownership after commit. A later install
may therefore immediately use the same memory id and version, even with a new
schema: the fresh `NeutronMemoryStore_<scope>` and old
`NeutronRetiredMemoryStore_<scope>` use distinct compiler import aliases while the old
null field is finalized. An explicit in-app `retired: true` declaration remains
an ownership tombstone and cannot be restored or reused by that app.

## Start With Memory V1

Use canonical manifest format 3 for every new app with persistent backend data.
The generated `neutron.lock.json` has its own format and remains format 2. A minimal
layout is:

```text
apps/notes/
  backend/
    main.mo
    memory/
      notes/
        v1.mo
  neutron.json
  neutron.lock.json       # generated by the first package build
```

The memory id in this example is `notes`. It is local to the app and must be a
valid Motoko-style identifier. The compiler combines the owner and local id in
every physical stable field, schema alias, migration alias, and retirement
field, so another app may independently use `notes` without a collision or
shared state.

Define the stable type and fresh-install defaults in `backend/memory/notes/v1.mo`:

```motoko
// Persistent schema: keep this file immutable after release. Package imports are
// allowed; relative imports are forbidden so app-local types cannot drift.
module {
  public type Mem = {
    var title : Text;
  };

  public func init() : Mem {
    { var title = "Untitled" };
  };
}
```

The schema may import declared Motoko packages such as `mo:core/Map`, `Set`,
`List`, or `Queue`. Use `Map` for keyed records, `Set` for membership, `List`
for growable random-access sequences, and `Queue` for FIFO state. Immutable
arrays remain appropriate for fixed snapshots and Candid vectors. A schema may
not import a relative app module. Do not place `Mem` in a shared
app-local `Types.mo` and alias it here: changing that file would silently change
every schema that references it. Put app-owned records and variants directly in
each version file, use pinned package collection types where appropriate, then
make runtime modules import the current schema. `mopack` enforces this boundary
for every schema version.

The app backend imports only the current schema:

```motoko
import Memory "./memory/notes/v1";

module {
  public type AppBackendEnvironment = {
    stable_memory : { notes : Memory.Mem };
  };

  public class Init(env : AppBackendEnvironment) {
    let mem = env.stable_memory.notes;

    public func /*query*/notes_title() : Text {
      mem.title;
    };
  };

  /*---NEUTRON GENERATED BEGIN---*/
  /* generated by npm run mogen */
  /*---NEUTRON GENERATED END---*/
}
```

Declare the memory root in the source `neutron.json`:

```json
{
  "format": 3,
  "id": "notes",
  "name": "Notes",
  "version": 100,
  "src": "main.mo",
  "memory": {
    "notes": {
      "version": 1,
      "schemas": {
        "1": {
          "src": "memory/notes/v1.mo"
        }
      },
      "migrations": []
    }
  }
}
```

Paths in memory declarations are relative to `backend/`. The generated actor
creates the persistent root, derives
`AppBackendEnvironment.stable_memory.notes`, and passes that one exact
environment to `Init`. Ordinary apps do not declare positional `init_arg`
resources; that field is kernel-only.

No migration is needed for the first schema, so an empty array is correct.

## Upgrade From V1 To V2

Suppose v2 adds a body. Do not edit `v1.mo`. Add a new schema:

```motoko
// backend/memory/notes/v2.mo
module {
  public type Mem = {
    var title : Text;
    var body : Text;
  };

  public func init() : Mem {
    {
      var title = "Untitled";
      var body = "";
    };
  };
}
```

Then add one migration edge:

```motoko
// backend/memory/notes/v1_to_v2.mo
import V1 "./v1";
import V2 "./v2";

module {
  public func migrate(old : V1.Mem) : V2.Mem {
    {
      var title = old.title;
      var body = "";
    };
  };
}
```

Change `backend/main.mo` to import `./memory/notes/v2`, then update the entire
memory declaration:

```json
{
  "format": 3,
  "id": "notes",
  "name": "Notes",
  "version": 101,
  "src": "main.mo",
  "memory": {
    "notes": {
      "version": 2,
      "schemas": {
        "1": {
          "src": "memory/notes/v1.mo"
        },
        "2": {
          "src": "memory/notes/v2.mo"
        }
      },
      "migrations": [
        {
          "from": 1,
          "to": 2,
          "src": "memory/notes/v1_to_v2.mo"
        }
      ]
    }
  }
}
```

The example deliberately uses app release `0.1.1` (packed version `101`) and
memory version 2. They do not need to match.

Each migration object has three required source-manifest fields and one
optional consolidation field:

| Field     | Meaning                                                                    |
| --------- | -------------------------------------------------------------------------- |
| `from`    | The old schema version accepted by the migration function.                 |
| `to`      | The new schema version returned by the migration function.                 |
| `src`     | The migration module path relative to the app's `backend/` path.           |
| `consume` | Optional ordered same-app roots that are retired and passed after `old`.    |

Schema object keys are JSON strings such as `"1"`; migration versions are JSON
numbers such as `1`.

The two defaulting paths are separate:

- a fresh v2 install gets values from `v2.init()`;
- an upgrade from v1 gets values from `v1_to_v2.migrate(old)`.

Changing `v2.init()` does not change an existing installation. Likewise,
`init()` is never called before or after a migration.

## Support A Skipped Upgrade To V3

A user may install the v3 package directly over v1. The v3 package must carry
all schemas and migration edges needed to reach v3 without installing the v2
package first.

For a normal linear history, add `v3.mo` and `v2_to_v3.mo`:

```motoko
// backend/memory/notes/v3.mo
module {
  public type Mem = {
    var title : Text;
    var body : Text;
    var tags : [Text];
  };

  public func init() : Mem {
    {
      var title = "Untitled";
      var body = "";
      var tags = [];
    };
  };
}
```

```motoko
// backend/memory/notes/v2_to_v3.mo
import V2 "./v2";
import V3 "./v3";

module {
  public func migrate(old : V2.Mem) : V3.Mem {
    {
      var title = old.title;
      var body = old.body;
      var tags = [];
    };
  };
}
```

The v3 memory declaration contains the complete linear path:

```json
{
  "memory": {
    "notes": {
      "version": 3,
      "schemas": {
        "1": { "src": "memory/notes/v1.mo" },
        "2": { "src": "memory/notes/v2.mo" },
        "3": { "src": "memory/notes/v3.mo" }
      },
      "migrations": [
        {
          "from": 1,
          "to": 2,
          "src": "memory/notes/v1_to_v2.mo"
        },
        {
          "from": 2,
          "to": 3,
          "src": "memory/notes/v2_to_v3.mo"
        }
      ]
    }
  }
}
```

With that package:

- installed v1 runs `v1_to_v2`, then `v2_to_v3`;
- installed v2 runs only `v2_to_v3`;
- installed v3 runs no migration;
- a fresh install runs only `v3.init()`.

Neutron composes the selected edges into one native Motoko migration expression,
so the complete change is one atomic canister upgrade.

## Direct And Repair Edges

An edge may skip versions. This is useful when an older edge is known to be
bad or when a direct conversion is materially safer. A target-v3 package that
supports v1 and v2 directly can declare:

```json
{
  "migrations": [
    {
      "from": 1,
      "to": 3,
      "src": "memory/notes/v1_to_v3.mo"
    },
    {
      "from": 2,
      "to": 3,
      "src": "memory/notes/v2_to_v3.mo"
    }
  ]
}
```

There must be exactly one path from the installed version to the target.
Do not publish this ambiguous graph:

```json
{
  "migrations": [
    { "from": 1, "to": 2, "src": "memory/notes/v1_to_v2.mo" },
    { "from": 2, "to": 3, "src": "memory/notes/v2_to_v3.mo" },
    { "from": 1, "to": 3, "src": "memory/notes/v1_to_v3.mo" }
  ]
}
```

For installed v1, that graph offers both `1 -> 2 -> 3` and `1 -> 3`.
Neutron rejects it instead of silently choosing one route.

Schemas do not need to be contiguous, but every edge's `from` and `to` version
must exist in `schemas`, every edge must move forward, and no edge may end above
the declared target version. One memory graph is limited to 64 schemas and 128
edges.

## Migration Function Rules

Every edge must export exactly this public shape:

```motoko
public func migrate(old : From.Mem) : To.Mem
```

Follow these rules:

1. Keep it synchronous. Do not use `async`, `async*`, `await`, actor calls, or
   HTTP outcalls.
2. Return the exact target `Mem` type. Neutron's Wasm compiler checks the edge
   against both schema modules.
3. Assign every new field explicitly. A target schema's `init()` defaults are
   not injected into migrated data.
4. Preserve every old value that still has the same meaning.
5. Rebuild a collection when its element type or representation changes.
6. Keep work bounded. A migration can trap or exhaust instructions, causing
   that installation to fail.
7. Never read another app's memory. `consume` accepts only same-owner roots
   retired in that same upgrade; the consumed values are staged for
   commit-atomic clearing after the migration has produced its target root.

Migration modules may import collection packages as well as their relative
source and target schemas. For example, a migration can iterate a v1
`Map.Map<K, V1>` with `Map.entries`, build a v2 map with `Map.empty`, and insert
converted values with `Map.add`; no copied internal map representation is
needed in either schema.

Schema `Mem` types must be stable Motoko data. Do not put functions, actors, or
transient runtime objects in persistent memory.

### Consolidate Same-App Roots

Prefer one memory root per app when its state has one lifecycle. The manifest
can consolidate older same-app roots as follows:

```json
{
  "memory": {
    "notes": {
      "version": 2,
      "migrations": [
        {
          "from": 1,
          "to": 2,
          "consume": ["notes_index"],
          "src": "memory/notes/v1_to_v2.mo"
        }
      ]
    },
    "notes_index": {
      "version": 1,
      "schemas": { "1": { "src": "memory/notes_index/v1.mo" } },
      "migrations": [],
      "retired": true
    }
  }
}
```

The edge signature becomes `migrate(old : V1.Mem, index : IndexV1.Mem) :
V2.Mem`. Consumed roots must be owned by the same app, active in the installed
release, and retired in the target release. The native migration can read each
consumed value while actor activation stages that retiring root; checked commit
then clears it atomically. A fresh installation of the target package needs no
destructive input and creates only the target root; historical retired
declarations remain ownership tombstones.

## Code-Only Releases

Do not increase a memory version for an ordinary frontend or backend code
release. Leave the memory declaration and current schema source unchanged:

```json
{
  "format": 3,
  "id": "notes",
  "name": "Notes",
  "version": 102,
  "src": "main.mo",
  "memory": {
    "notes": {
      "version": 2,
      "schemas": {
        "1": {
          "src": "memory/notes/v1.mo"
        },
        "2": {
          "src": "memory/notes/v2.mo"
        }
      },
      "migrations": [
        {
          "from": 1,
          "to": 2,
          "src": "memory/notes/v1_to_v2.mo"
        }
      ]
    }
  }
}
```

Compared with the schema-upgrade example, only the app release changed from
`0.1.1` (`101`) to `0.1.2` (`102`). The memory version, schemas, and migrations
stayed byte-for-byte identical.

A managed schema hash is immutable at a given memory version. Editing `v2.mo`
or changing `v2.init()` while still declaring memory version 2 is rejected. The
schema identity hashes only the comment-stripped version file, not imported
package contents. A dependency update can change the executable entry and is
still subject to Motoko type checking and stable-signature compatibility.

## Packaging And `neutron.lock.json`

Run the app's normal package command:

```sh
npm run package
```

For managed memory, `mopack`:

1. Packages the app entry, every declared schema, every declared migration,
   and all their transitive imports.
2. Writes content-addressed modules under `dist/mo/<sha256>.mo`.
3. Adds a source-only `hash` and executable `entry` beside each schema `src` in
   `dist/neutron.json`.
4. Creates or verifies the root `neutron.lock.json`.
5. Copies the verified lock into the final `.neutron` package.

Write only `src` in the source manifest. `hash` and `entry` are generated and
are rejected when hand-written in the source `neutron.json`.

Commit `neutron.lock.json`. Once a schema version or migration edge has shipped,
do not edit its source. The lock compares a schema's source-only hash, while a
migration edge remains locked by its complete packaged closure. It permits new
versions and edges but rejects changes to released lineage. If an obsolete edge
is removed from the active graph, its lock record remains as history.

Removing a schema or all paths from an old version also stops the new package
from upgrading an installation that still has that version. Do so only as an
explicit support-policy decision, not as package cleanup.

Use pinned dependency versions in schema and migration closures. A moving Mops
branch can change executable types or a migration entry even when a schema root
file was not edited.

## Multiple Private Memories

An app may own multiple roots:

```json
{
  "memory": {
    "notes": {
      "version": 1,
      "schemas": {
        "1": { "src": "memory/notes/v1.mo" }
      },
      "migrations": []
    },
    "preferences": {
      "version": 1,
      "schemas": {
        "1": { "src": "memory/preferences/v1.mo" }
      },
      "migrations": []
    }
  }
}
```

Declaring a root makes the app its owner. Another app cannot claim, receive,
migrate, consume, retire, or restore it. The assembler derives both active
fields in one exact group:

```motoko
public type AppBackendEnvironment = {
  stable_memory : {
    notes : NotesMemory.Mem;
    preferences : PreferencesMemory.Mem;
  };
};
```

Cross-app composition uses domain-owned functions, not memory. The owner keeps
all state access behind explicitly exported internal functions, and consumers
declare exact minimum-version dependencies. See
[Backend App Dependencies](./backend-app-dependencies.md).

## Retire One Memory Root

Retirement permanently removes one root while leaving the app installed. Keep
the historical declaration, set `retired: true`, and remove its field from the
app's local `AppBackendEnvironment.stable_memory` type:

```json
{
  "memory": {
    "notes": {
      "version": 3,
      "schemas": {
        "1": { "src": "memory/notes/v1.mo" },
        "2": { "src": "memory/notes/v2.mo" },
        "3": { "src": "memory/notes/v3.mo" }
      },
      "migrations": [
        { "from": 1, "to": 2, "src": "memory/notes/v1_to_v2.mo" },
        { "from": 2, "to": 3, "src": "memory/notes/v2_to_v3.mo" }
      ],
      "retired": true
    }
  }
}
```

The app's current `Init` class must no longer read
`env.stable_memory.notes`. If no other backend resources remain it changes to
`Init()`; otherwise it keeps one environment with only the remaining groups
and fields. The compiler stages the old value through activation, clears it in
the checked journal commit, and finalizes the null field on the next upgrade.
The manifest keeps the memory id owned and tombstoned afterward.

Deleting the `memory.notes` property without `retired: true` is rejected. It is
never interpreted as permission to discard data.

## Uninstall The App

Full uninstall is not a manifest edit. Use the reviewed launcher uninstall
action when testing the product workflow. For the normal local development
loop, remove the app archive's path declaration from the format-3 PocketIC
artifact set and run the provisioner's destructive whole-canister reinstall;
there is no
package-level uninstall CLI.

Neutron compiles a target actor without the app, verifies the new runtime, and
removes its registry entry, web/package assets, connection credentials,
backend-call reservations, message-bus session state, resident frame, and
workspace tiles in the checked commit. Every live managed root is staged and
cleared by the commit-atomic retirement protocol described above.

If the app reserved app-isolated vetKeys slots, uninstall retires them only in
the verified install-journal commit. An aborted or failed actor activation
preserves the old slots and their namespace nonces. A later reinstall with the
same textual app/slot ids receives a new random nonce and never-reused slot uid,
so it does not recover the old installed instance through supported APIs.
Compatible updates preserve slots; removing a slot declaration suspends it at
commit rather than deleting it, and re-adding it requires explicit enable.

Uninstall is blocked while another installed app declares a backend function
dependency on the app. The kernel app cannot be uninstalled.

After successful uninstall commit, the removed app no longer owns its memory
ids. A replacement app can claim one immediately; the compiler finalizes the
old null retired field independently from the replacement's fresh active root.

Neither memory retirement nor vetKeys retirement is cryptographic erasure. An
active controller can restore an earlier snapshot or replace code, and a key
already recovered or copied by a browser/app remains usable against retained
ciphertext. Restore plans must preserve the kernel v1 slot registry and
consuming-app ciphertext consistently; moving the data to a different Neutron
canister principal changes the vetKD namespace. See
[App-Isolated vetKeys](./app-isolated-vetkeys.md).

## Test Before Publishing

At minimum, test all of these cases with real non-default data:

1. Fresh target-version install uses the target `init()` defaults.
2. Every prior version advertised by the target package reaches the target
   through exactly the expected edges.
3. The oldest supported version upgrades directly to the newest package.
4. A code-only release preserves state without running a migration.
5. A migration failure leaves the old actor and active package metadata usable.
6. Retirement and consolidation preserve data through activation, clear it in
   checked commit, and finalize the null field on the following upgrade.
7. An app with live roots uninstalls through the checked journal, immediate
   same-id reinstall compiles, and backend dependents still block provider
   uninstall.

The compiler's pure lifecycle suite can be run with:

```sh
npm --workspace neutron-compiler test
```

Those tests cover multi-edge migration planning, uninstall retirement, staged
retirement metadata, and null-checked finalization without mutating a running
local Neutron. Local baselines must be emitted by a trusted package workflow,
pinned in a format-3 provision artifact set, and installed through the
provisioner's whole-canister reinstall. Exercise an actual app update through
the Kernel's product update UI; do not use a test-only incremental deploy
command. Retain the exact released v1 and v2 packages used by app-specific
tests. Rebuilding an old package from current source is not a historical
compatibility test.

## Common Errors

| Error                                      | Cause and correction                                                                                             |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `schema hash changed`                      | A released schema file changed. Restore it and add a new package-only schema version instead.                    |
| `no migration path`                        | The target package omitted a schema or edge needed by the installed version. Include one complete path.          |
| `ambiguous migration paths`                | More than one route reaches the target. Remove obsolete edges from the active graph or publish one direct route. |
| `removed memory without declaring retired` | Put the declaration back and publish it with `retired: true`; omission alone never authorizes data destruction. |
| `cannot downgrade`                         | Memory versions only move forward. Publish a newer corrective schema.                                            |
| `requires a different schema hash`         | Update the foreign consumer requirement together with the owner package.                                         |
| lock verification failure                  | A locked schema source or migration closure changed. Do not overwrite released history.                          |

## What Neutron Verifies

Before active metadata changes, Neutron validates ownership, graph structure,
the unique selected path, content hashes, dependency reachability, migration
security policy, generated Motoko types, and stable-signature compatibility.
Mutable assets are staged, the actor upgrade is dispatched, and
`kernel_runtime_info` is polled before the install journal commits them.

A migration can still be computationally too expensive or trap on particular
data. The runtime then rejects the actor upgrade and leaves the previous actor
active. App-specific migration tests remain required.
