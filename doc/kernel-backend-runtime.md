## Implementation Facts

### Module Shape And `Init`

`apps/kernel/backend/main.mo` is a Motoko module, not the deployed actor. It
exports:

- `Init`, a class that receives the managed kernel schema `Mem`, the generated
  activation schema, generated running deployment id, and complete generated
  app-instance inventory plus the canister principal, then exposes the module's
  runtime functions;
- Generated input/output type aliases consumed by the actor wrapper.

The deployed actor lives in `apps/kernel/backend/_neutron.mo`, which is marked
as autogenerated. It imports `main.mo` as `NeutronModule_a6_kernel`, creates
persistent `NeutronMemory_a6_kernel_r6_kernel`, instantiates the module's `Init`
with that root plus the separate activation root as `NeutronKernel`, with the
generated deployment id and
`NeutronActiveAppInstanceInventory`, and exposes the public Candid methods
declared in `apps/kernel/neutron.json`.

The manifest declares the kernel app as:

- `id`: `kernel`
- `src`: `main.mo`
- `format`: `3`
- packed release version: read from `apps/kernel/neutron.json`; this guide does
  not pin the active release
- `init_arg`: `memory_kernel`, `memory_kernel_activation`, `deployment_id`, and
  `active_app_instance_inventory`, plus `canister_principal`
- one `kernel` memory schema at v3 and one
  `kernel_activation` schema at v1, both with no predecessor or migration edge

Versions 3 and 1 are released production memory history. Their schema sources
and existing `neutron.lock.json` entries are immutable. A code-only Kernel
release retains both versions and restores the existing roots; it does not add a
fake migration. Discarded split-root and earlier development-only shapes remain
unsupported, but that exception is not a release path for an installed
production Neutron. See
[Managed Memory Migrations And Uninstall](./memory-migrations-and-uninstall.md)
and the [v0.3.7 GPL bridge candidate checklist](./license-and-deployment-records.md#historical-v035-and-v036-to-v037-gpl-bridge-candidate-checklist).

`apps/kernel/moassemble.ts` reads `neutron.json`, fills `entry` from `src`, and
writes `backend/_neutron.mo` through `packages/neutron-compiler/src/assemble.ts`.

### Persistent Memory Model

`Memory_kernel` v3 is one app-owned record with twelve fields:

- `core`, containing assets, authorization, and certification state;
- `connections`, containing OAuth flows and credentials;
- `install`, containing the pending deployment journal;
- `backend_calls`, containing persistent app-bound call reservations;
- `capability_registry`, containing exact runtime-resource enable state and
  bounded usage summaries;
- `app_usage`, containing exact-installation saturating `Nat64` instruction and
  execution totals plus exact unbounded `Nat` outgoing gross/refund and accepted
  incoming-cycle totals, with sparse rolling 30 UTC-day buckets;
- `chain_key_signing`, containing exact signing-slot state, public-key caches,
  and immutable namespace fingerprints;
- `stable_store`, containing app/install/store-isolated dynamic binary records,
  revisions, quotas, and logical usage;
- `certified_assets`, containing AppScope-owned mounts, route records, and
  per-scope/global entry and byte accounting;
- `http_post_update_handlers`, containing AppScope-owned POST mounts, fixed-hour external-traffic rate
  counters, bounded replay/tombstone records, reserved bytes, and pending
  accounting;
- `public_ingress`, containing exact inter-canister protocol routes, external-traffic rates,
  pending dispatches, and authority epochs; and
- `vetkeys`, containing app-isolated slot namespace/lifecycle metadata,
  public-key caches, lifetime accounting, tombstones, and audit facts.

`install` and `connections` are fields of this one `kernel` memory object, not
independent managed-memory roots. The former `kernel_install` and
`kernel_connections` schema directories belonged to the discarded split-root
development model and are not part of the v3 baseline.

`Memory_kernel_activation` v1 is intentionally a separate managed root. It
contains only:

- optional 32-byte activation hash;
- optional principal that armed it; and
- a consumed flag.

Separating this new one-time bootstrap state avoids changing the established
kernel v3 stable signature.

The nested `core` record contains:

- `assets : Map.Map<Text, Asset>`
- `authorized : Set.Set<Principal>`
- `cert : CertTree.Store`

The remaining persistent collections are selected by behavior:

- OAuth flows use `Map.Map<Blob, OAuthFlow>`;
- saved connections use `Map.Map<Text, Connection>`;
- backend-call reservations use `Map.Map<Nat, BackendCallReservation>`; and
- runtime capabilities use a bounded `Map.Map<Text, CapabilityRegistryEntry>`
  keyed by exact app scope, kind, and resource; and
- HTTP POST update-handler replay is keyed by a domain-separated `Blob` digest, while
  per-mount/per-scope rate and quota counters use exact scoped text keys.

Connection flows and credentials carry the exact kernel-assigned app scope,
provider, and requested scopes. Actor construction only
loads the compiler declaration table. The install service promotes the target
app-instance inventory first, then its synchronous commit callback removes
records whose exact declaration no longer exists; a pending or aborted install
therefore cannot delete the predecessor deployment's usable credential.

The `mem.install` field also stores one browser-origin epoch captured from
`Prim.canisterVersion()` when the fresh app-instance inventory is initialized.
Browser-origin nonces bind that stable epoch, app ID, installation UID, and
issuance canister version. Ordinary upgrades retain committed identities;
removing and adding an app allocates a new UID, and a full canister reinstall
changes the IC canister version.

New installation UIDs are allocated from a bounded lane derived from the
non-rollbackable canister version. Immediately before sending an upgrade,
`markDispatched` reissues the pending target in the current version lane in the
same message that certifies the dispatch marker. For transactions whose
predecessor implements this rule, restoring a snapshot taken before dispatch
cannot reuse an installation UID or origin nonce that a discarded branch
already activated. This uses no asynchronous randomness call during actor
initialization.

`Assets.Doc` stores the static asset key, chunk count, blob chunks, content
encoding, and content type. `Assets.use(init)` wraps the Core map with the small
asset-specific lookup API used by `main.mo`. Fixed blob chunk vectors and
install-journal vectors remain immutable arrays because they are indexed or
captured as one transaction snapshot.

The generated actor is a modern `persistent actor class` with Motoko's
`<system>` capability, and wraps kernel memory in a version variant:

```motoko
import NeutronModule_a6_kernel "<kernel module>";
import NeutronMemorySchema_a6_kernel_r6_kernel_v3 "<kernel schema>";
import NeutronMemorySchema_a6_kernel_r17_kernel_activation_v1
    "<kernel activation schema>";

type NeutronMemoryType_a6_kernel_r6_kernel = {
    #v3 : NeutronMemorySchema_a6_kernel_r6_kernel_v3.Mem;
};
type NeutronMemoryType_a6_kernel_r17_kernel_activation = {
    #v1 : NeutronMemorySchema_a6_kernel_r17_kernel_activation_v1.Mem;
};

let NeutronMemoryStore_a6_kernel_r6_kernel :
    NeutronMemoryType_a6_kernel_r6_kernel =
    #v3(NeutronMemorySchema_a6_kernel_r6_kernel_v3.init());

transient let #v3(NeutronMemory_a6_kernel_r6_kernel) =
    NeutronMemoryStore_a6_kernel_r6_kernel;
let NeutronMemoryStore_a6_kernel_r17_kernel_activation :
    NeutronMemoryType_a6_kernel_r17_kernel_activation =
    #v1(NeutronMemorySchema_a6_kernel_r17_kernel_activation_v1.init());
transient let #v1(NeutronMemory_a6_kernel_r17_kernel_activation) =
    NeutronMemoryStore_a6_kernel_r17_kernel_activation;
transient let NeutronActiveAppInstanceInventory =
    [<generated active app instances>];
transient let NeutronKernel = NeutronModule_a6_kernel.Init(
    NeutronMemory_a6_kernel_r6_kernel,
    NeutronMemory_a6_kernel_r17_kernel_activation,
    "<generated deployment id>",
    NeutronActiveAppInstanceInventory,
    NeutronPrim.principalOfActor(NeutronActor),
);
```

In a persistent actor, plain actor fields are stable by default. The generated
wrapper therefore no longer uses `stable let`; the runtime-only destructuring
and `Init` object are explicitly `transient`. The length-delimited
`a6_kernel_r6_kernel` stem is the compiler-owned physical namespace for
`(app id = kernel, local memory id = kernel)`. Manifests, runtime inventory,
and the projected app environment continue to use the local id `kernel`.
The compiler and install verifier publish the active memory inventory in
canonical `(owner app id, local memory id)` order. Equal local ids in different
apps remain distinct; a duplicate pair, missing root, schema mismatch, or
noncanonical runtime list fails deployment verification. Retirement metadata
uses the matching version marker and the same exact pair as its identity.

The relationship is:

1. `backend/memory/<id>/vN.mo` owns the persistent `Mem` type and `init()`.
2. `neutron.json` declares the memory id, version, and schema source.
3. `_neutron.mo` creates the version wrapper and passes the unwrapped memory,
   deployment id, and app-instance inventory into the namespaced kernel
   initializer.
4. Runtime methods mutate the shared memory record through `NeutronKernel`.

The v3 schema defines its complete app-owned stable structure in one versioned
file. It may import declared package collection types such as `mo:core/Map`, but
it cannot import local runtime modules. Runtime asset, connection, install,
backend-call, capability-registry, app-usage, stable-store, vetKeys, and certification
modules consume those structural types; the dependency direction never points
from a schema into mutable runtime code. Future persistent changes after this
baseline is released add immutable schema versions and reviewed migration
modules instead of editing released history.

`backend/backend_calls/` separates persistent lookup (`Memory.mo`),
public and app-bound types (`Types.mo`), policy and batching (`Service.mo`), and
the raw transport (`Raw.mo`). The assembler configures installed declarations
and gives each declaring app one field inside its generic capability record.
`backend/capabilities/Registry.mo` owns the generic runtime-resource lifecycle,
owner kill switch, saturating outcome counters, and bounded Settings pages.
Specialized services keep their typed reservations, key lifecycle, credentials,
quotas, cost ceilings, and target policy. Capability services have no
time-window request-rate limits. `backend_calls` is the deliberate financial
exception: its manifest declares gross cycles per call and a net-plus-unresolved
UTC-day cycle ceiling, while zero-cycle calls remain free of a temporal request
counter. Awaiting broker operations capture an actor-local
registry epoch lease; disable followed by re-enable cannot revive an operation
that was already suspended under the old epoch.

The registry also owns an actor-local `Nat64` capability-authority revision.
Each successful owner toggle advances it only after capability-specific
reconciliation succeeds. The generated runtime query returns it alongside the
deployment ID; the frontend treats either value changing as global app-frame
and transient-grant invalidation. A replacement actor may start the local
counter again because its deployment ID must also change.

`backend/scheduler/` owns static timer setup, transient overlap state, and
per-run backend-call budget and lease activation. It has no separate persisted
disabled-task store: the task's exact generic registry entry is authoritative.
Timers are recreated from the assembled declarations after installation and
upgrade. Callback completion or failure closes its fresh invocation lease, and
owner disable closes a running lease immediately.

The same module owns the smaller declaration-free `DeferredTimersV1` backend
leaf. It accepts at most eight active logical keys per exact app installation,
with 1-40 character keys and one-shot delays from 10 seconds through 30 days.
Arming an existing key returns its original deadline instead of postponing it.
Only the kernel holds the Motoko timer id; the app has no cancel, recurring, or
raw timer operation. Callback execution is charged to the app usage ledger,
checks committed deployment and exact-scope liveness, and removes the key at
completion. The callback type is synchronous, so it cannot await, make a
backend call through this interface, or request recurrence. A trapping callback
leaves an overdue logical key that the next ordinary arm safely replaces;
native callbacks carry a generation id so an old delivery cannot run
replacement work. The map and pending native timers are intentionally
transient across actor upgrades.

`backend/app_usage/` is kernel-owned operational accounting rather than
an app capability. Generated wrappers sample `Prim.performanceCounter(1)` at
the beginning and end of ordinary app update entrypoints, scheduled callbacks,
and both the broker and self-handler messages for HTTP POST and public-ingress
updates. Counter 1 spans awaits in the current call context but excludes nested
remote/self execution, which is independently charged when it enters another
metered wrapper. Queries are not measured. Returned errors and catchable timer
errors reach the final sample; a trap rolls the sample write back with the
trapped message.

The ledger is keyed by exact `AppScope`. It keeps saturating `Nat64`
instruction and execution totals plus sparse buckets for the current UTC day
and 29 predecessors. Outgoing gross/refund counters and accepted incoming
cycles use exact unbounded `Nat` arithmetic at day, window, and installation-
lifetime scope; those cycle totals never saturate. These measures remain
separately typed. Outgoing accounting is explicitly two-phase. Before dispatch,
`reserveOutgoingCycles` books only the gross explicit attachment and its
financial allowance while retaining the intended call count.
`commitOutgoingDispatch` is invoked exactly once immediately before the
remote dispatch and adds 260,000 cycles per call. A known pre-dispatch failure
uses `cancelOutgoingReservation`, which unwinds the explicit reservation and
adds no call base. After a committed dispatch, `finalizeOutgoingCycles`
settles the explicit gross amount to the observed `attached - refunded`
charge. An unexpected interruption with no observable refund remains
conservatively gross, while the already committed call base remains charged.

The same lifecycle counts zero-attachment management calls: app-attributable
`raw_rand` dispatches for randomness, Connections, and vetKey slot nonces, plus
uncached chain-key and vetKey public-key lookups, each add the 260,000-cycle
13-node request/response base. A cache hit or a failure canceled before
dispatch adds no base. The outgoing-cycle accumulator also retains 1,200,000
cycles of ingress reception for each authorized update and 260,000 cycles for
each measured timer/handler self-call. Paid canister public updates add no
ingress reception fee because their calling canister owns the inter-canister
call charge; direct authenticated ingress does add that fee.
Variable message transmission, storage, and kernel maintenance costs are not
presented as app-attributable cycle transfers. A paid public update records
exactly the cycles accepted from its immediate caller in the incoming measure.

Raw-call batches use one aggregate reservation carrying the batch call count,
commit that count at dispatch, and finalize after all batch futures complete.
A slow sibling can therefore delay known refunds from the others, and
continuation loss may retain the batch gross. This is a safe overcount rather
than a spending-limit bypass or undercount.

`kernel_app_usage_snapshot` returns only active scopes through a bounded
authenticated query. Its instructions, executions, outgoing cycles, accepted
incoming cycles, and sparse daily buckets remain separately typed raw
telemetry. Settings joins the active
scope into its Installed Apps row and applies the low-side 13-node rates: one
cycle per lifetime instruction, 5,000,000 cycles per measured update execution,
and lifetime outgoing cycles containing the 260,000-cycle base per brokered
call, zero-attachment `raw_rand` or uncached management public-key call, or
measured timer/handler self-call, the 1,200,000-cycle ingress base per
authorized or direct-authenticated-ingress update, and net explicit transfers.
It rounds the result to four decimal places in `TC`. At the current IC rate
table for a 13-node subnet, one
Wasm instruction really costs one cycle; this is IC platform pricing, not a
Neutron product convention. The rate remains subnet- and rate-table-dependent.
Each CDK scheduled-task self-call contributes both its 260,000-cycle
request/response base and, through the measured callback wrapper, a
5,000,000-cycle update-execution base. The shared Motoko global-timer dispatch
that initiates that work remains omitted. Variable byte fees,
response-callback bases, storage, and compute allocation also remain excluded,
so Neutron's attribution is deliberately low-side and non-billing-grade. In
developer mode, the same Installed Apps entry exposes the separately typed
30-day and installation totals when expanded; normal mode keeps the overview
total and omits that raw diagnostic breakdown.
Incoming cycles are attribution, not negative usage: they show how much a paid
public-update route accepted for that app and do not hide the receiver's
measured work. Commit cleanup removes retired installation scopes, so an
uninstall/reinstall cannot inherit old usage.

`backend/certified_assets/` owns the generic app-scoped certified asset engine,
and `backend/certified_http_v2.mo` owns its closed request/response profiles.
The authored `certified_assets.api: 2` value versions the declaration and
backend handle; it does not select an authored HTTP-route API. The assembler
captures the exact app installation scope and injects the handle only for an
install-reviewed declaration. App code sees typed collection operations, never
scope text, raw routes, arbitrary headers, certification primitives, or shared
memory.

The engine supports exactly three generic collection kinds:

- `publication`: opaque host-bound objects, staged create-once mutation, and
  certified `GET`/`HEAD` with bounded ranges;
- `immutable_blob`: body-SHA-256-addressed objects under a declared prefix,
  inline or staged create-if-absent, and portable certified `GET`; and
- `mutable_blob`: keyed-prefix or exact-path objects, inline CAS mutation, and
  portable certified `GET`.

The compiler synthesizes `certified_read_routes` for collection mounts under
`/app/<app-id>/_route/<mount-id>`. Authored `http_routes` remains the separate
API-1 bounded POST-update surface. Persistent storage, the authenticated
forest, quotas, staging, conditional mutation, certified absence,
install-journal reconciliation, runtime toggles, maintenance, and physical
admission are specified in
[Certified HTTP And Certified Assets](./kernel-http-v2-and-certified-assets.md).

`backend/http_post_update_handlers/` owns bounded public POST admission and replay. Its
committed mounts contain exact `AppScope`, surface and public base,
request/reply/rate/header bounds, complete authority fingerprint, and epoch.
The assembler registers one
compiler-owned self-only callback for each exact internal synchronous handler;
the app receives no dispatcher or durable HTTP capability handle.

`http_request` performs only bounded preflight for an exact POST and asks the
gateway to upgrade. `http_request_update` repeats Host, path, body, headers,
registry, liveness, fingerprint, and idempotency validation. An anonymous HTTP
gateway caller durably consumes the fixed-hour mount/app/global external-
traffic window before the handler self-call. A direct Candid invocation by a
kernel-authorized principal is neither limited nor counted. Both paths reserve
replay bytes and retain every route, capacity, concurrency, lifecycle, and
cycle check. One pending call is permitted per mount, two per app,
and eight globally; the canister admits at most 1,024 calls/hour and retains at
most 1,024 replay records/64 MiB. Handler dispatch immediately rechecks the
pending record and authority epoch, invokes app code synchronously, validates
the closed status/content-type/body reply, and commits the exact replay before
the self-message returns. New admission stops below a 250 billion-cycle reserve.
On a later valid dispatch, a pending record older than five minutes lazily
becomes outcome-unknown without redispatch; one-hour replay expiry is likewise
reaped lazily by later dispatch/configuration work. A trap cannot roll admission
back or make retry free. There is no
separate V1 per-handler instruction allowance below the IC update-message
limit. The outer broker and inner compiler-bound handler are, however, measured
as separate instruction executions for Settings. External-rate/concurrency
bounds and the cycle reserve do not cap one handler's execution cost more
tightly.

After the self-call returns, the outer update rechecks the current fingerprint
and authority epoch. A disable or declaration change in that interleaving
window returns `revoked`/HTTP 503 even though the handler mutation and replay
may already be committed. Clients must treat that result as ambiguous and keep
the same idempotency key; an exact re-enable replays the completion, while a
changed fingerprint conflicts rather than dispatching again.

Every request requires `Idempotency-Key`. Stable state stores its
domain-separated hash and a hash of the handler-visible request, never the raw
key. For one hour, a completed exact duplicate returns the stored reply without
app execution; changed input is `409`; pending, failed, or unknown state never
redispatches. Runtime disable denies every POST including replay. Exact
re-enable may replay a compatible completion, but pending work from an old
epoch cannot execute. Commit removes changed/removed bindings and per-mount
rates but deliberately retains their one-hour replay tombstones and quota: a
changed same-id request conflicts and a removed mount is unreachable. Uninstall
or an inactive `AppScope` purges that scope's counters, replays, and bindings.

Forwarded values are capped at 4,096 bytes and a declared name may occur only
once. Cookie/Set-Cookie headers, duplicate declared headers, and duplicate or
non-`identity` Content-Encoding reject the entire request; they are not merely
removed before app code.

The broker's own fixed errors map invalid/not-found/method/body to
400/404/405/413, conflict or failed-unknown to 409, pending to 425, and an
exhausted external request window to 429. Busy, replay-capacity, low-cycles, or
revoked results use 503, and handler failure uses 500. These are not
app-selected handler statuses and V1 adds no `Retry-After` header.

If a target actor activates before its checked install journal commits, the
service removes the retained routes' exact proof owners and refuses route
resolution. It preserves the scoped bytes as recovery state, not usable public
authority. Checked commit reconciles them and republishes only unchanged mounts
that the newly committed registry enables.

`backend/public_ingress/` owns public Candid protocol admission separately from
ordinary app methods. Each committed route is keyed by exact `AppScope`,
protocol, and route id and binds mode, caller class and optional update
`required_cycles` floor,
byte/rate limits, handler, declaration fingerprint, and authority epoch. The generic registry owns the
runtime toggle at `public_ingress/<protocol:id>`. A compiler-generated physical
endpoint captures app, protocol, and mode; the bounded request contains only
`method : Text` and a nested Candid `payload : Blob`. The real IC caller is
passed separately by the wrapper and cannot be forged in the payload.

Query dispatch checks scope, registration, mode, its declared principal caller
policy, request/reply limits, handler, and live registry lease, then invokes
the exact compiler-registered synchronous closure without an await. Query
routes have no hourly rate, pending, or cycle charge.

An update route is either direct authenticated ingress or a paid
inter-canister protocol. `caller: "authenticated"` forbids `required_cycles`
and admits only a self-authenticating principal; anonymous and canister
principals are rejected and no cycles are accepted. Its outer message records
the 1,200,000-cycle ingress-reception base. `caller: "canister"` requires a
positive `required_cycles` floor. Its exact synchronous handler may opt into
`public_ingress_cycles`; when it also requests the caller, the canonical
ordered arguments are `["caller", "public_ingress_cycles"]`. Every route
targeting an opting-in handler must be a canister update. Underpayment traps.
After exact route resolution and a valid floor, the kernel accepts and
attributes that amount before payload, reserve, pending, or rate checks, so a
funded later rejection
retains the floor. No app constructor, query, authenticated-ingress handler, or
unrelated method receives the cycles value. Opting in also suppresses the
handler's ordinary owner-authorized actor wrapper; apps needing an owner path
must declare a separate method over shared internal logic.
The isolated handler is a separate self-call and records its 260,000-cycle base
for either variant.

Update dispatch then performs the ordinary route checks plus a 250-billion-
cycle receiver floor, an optional caller-first fixed-hour rate, shared
route/app/global fixed-hour rates, and pending limits of one/two/eight. A
caller-window rejection consumes no shared capacity. The receiving Neutron
must already have enough balance to
pass its reserve check; the payment is neither emergency funding nor a bound on
the handler's instruction use. It persists a dispatch id, request hash, fingerprint,
epoch, real caller, and lease before awaiting the compiler-generated self-only
update switch. That switch rechecks the complete binding, synchronously invokes
one exact handler, and records the bounded response. A trap maps to
`#handler_failed` and rolls back that self-call's app mutations without
refunding accepted outer admission. The broker and self-handler messages are
separately measured for the same app installation.

Within an opting-in paid handler, `public_ingress_cycles.available()` returns
the captured still-unaccepted surplus minus amounts already requested.
`request(amount)` accumulates a supplemental request and traps if `amount`
exceeds that remainder; neither operation directly accepts cycles. The cycles
value is a compiler-injected trailing argument, not Candid payload data or an
app environment field. The outer dispatcher attempts the accumulated request
only after the handler self-call commits its app mutations and the live route,
lease, fingerprint, authority epoch, and persisted completion still validate.
Post-commit revocation returns `#revoked_after_dispatch` without accepting the
supplement. Supplemental acceptance is therefore best-effort and non-atomic
with app state: it cannot roll back irreversible work. A route's
`required_cycles` floor must cover all such work without relying on the
supplemental request; any surplus that remains unaccepted is refunded.

Each update route declares at most 3,600 calls/hour; each app
installation is capped at 3,600 and the actor at 16,384 across public-ingress
update traffic. Pending records become stale after
five minutes and interrupted records are recovered when the service is
reconfigured. After the self-call, the outer dispatcher rechecks the lease,
fingerprint, and epoch. A committed handler followed by concurrent revocation
returns `#revoked_after_dispatch`, so the mutation may exist even though the
response is withheld.

Checked install commit preserves rate and epoch only for an exact unchanged
route fingerprint, advances authority for changed routes, and removes obsolete
or uninstalled route state. New app scopes stay inactive until the full journal
commits. Disabling a registry resource advances the broker epoch and discards
its pending records. The registry audit counts bounded outcomes and stores no
protocol payloads.

`backend/https_outcalls/` owns paid external HTTPS dispatch. Its declaration
table maps exact `AppScope` and endpoint id to one canonical URL prefix,
GET/HEAD/POST subset, header allowlist, request/reply bounds, and the fixed
`strip_headers` transform. The scoped
capability factory closes over `AppScope`; request data contains no app id,
absolute URL, cycle amount, transform callback, or replication choice.

The service canonicalizes and bounds a relative path (1,024 UTF-8 bytes and 64
segments), query pairs, headers, body, and POST idempotency key before dispatch.
It quotes the current platform cost, enforces one/two/eight
endpoint/app/global concurrency and a 250-billion-cycle reserve, and returns
`#cost_too_high` for a quote above the 50-billion-cycle per-call ceiling. It
keeps no fixed-hour call or cycle counter. The
management adapter always requests replicated execution and installs the one
management-caller-only transform, which returns status/body with headers
removed. Observed redirects and raw rejects collapse to closed results.

Every paid dispatch captures the exact endpoint registry lease and repeats
scope, declaration, fingerprint, and lease checks after the await. Revocation
suppresses response bytes but cannot undo cycles already charged or a remote
POST side effect. Endpoint authority reconciles only after checked install
commit; uninstall purges the old scope. The generic registry records bounded
endpoint/method outcome totals. There is no separate persistent rate state.
Neither audit nor app-usage telemetry stores HTTP status,
byte totals, raw rejects, or request/response content.

`backend/chain_key_signing/` owns app-isolated threshold assertion signing.
The compiler supplies exact slot declarations and a trusted environment key map;
app code receives only a source-bound `public_key(slot)` /
`sign_assertion({slot; assertion})` leaf. Namespace construction hashes the
fresh kernel-install epoch, canister principal, exact app scope, slot,
algorithm, and resolved key name into the sole opaque 32-byte management
derivation component. A second domain binds the fixed app-assertion format, and
the broker hashes that domain plus the bounded assertion before signing.

The broker normalizes ECDSA public keys to compressed SEC1, BIP340 to x-only,
and Ed25519 to 32 bytes, discarding the management chain code. Production uses
`key_1`; local assembly exposes only ECDSA `dfx_test_key` and returns
`#key_unavailable` for Schnorr without fallback. The app cannot select a master
key, derivation path, raw digest, transaction, BIP341 auxiliary data, attached
cycles, or retry behavior.

Signing enforces 1/2/4 concurrency, returns `#cost_too_high` for a quote over
the 50-billion-cycle per-call ceiling, and preserves a 250 billion-cycle
reserve. It has no fixed-hour signing, public-key, or cycle counters. A
validated public key is cached per slot. Each uncached public-key management
dispatch contributes the fixed 260,000-cycle call base; a cache hit contributes
no remote-call base. The post-await path rechecks the exact registry lease and
declaration/identity fingerprint; revocation suppresses returned signature
bytes but cannot undo the paid threshold call. Ambiguous system/canister errors
return `#outcome_unknown` and are never retried. State and audit store no
assertion, digest, signature, management request, or raw reject. See
[App-Isolated Chain-Key Assertion Signing
V1](./app-isolated-chain-key-signing.md).

`backend/stable_store/` owns app-isolated dynamic binary key/value storage in
kernel-owned nested Core Maps. The compiler-created factory captures exact
`AppScope`; each store record adds its declared id and a monotonically
allocated, never-reused namespace uid. App code receives no scope, map,
Region, stable-memory pointer/offset/page, namespace allocator, or registry
object.

The synchronous broker provides one-key get, conditional put,
revision-checked delete, bounded live prefix list, scoped usage, and bounded
prefix cleanup. Put stamps the current declared schema version and allocates a
monotonic revision. Live cursors contain only namespace generation, prefix,
and last logical key; range iteration seeks with `Map.entriesFrom` and stops
outside that prefix. Mutations reject non-replicated query execution rather
than claiming that rolled-back query state persisted.

Store/app/global entry and payload-byte limits, key/value/page bounds, stable
put and rewritten-byte admission, and a canister cycle reserve limit growth.
A narrowed over-quota store remains readable and cleanable and accepts only a
target-valid, non-growing replacement until it fits. The app owns lazy migration by
examining each entry's write-time schema version and rewriting with CAS; the
kernel never decodes values.

The install service reconciles stable stores only in checked commit. Identical
scoped ids retain data and revision state; pending or aborted deployment
cannot use or remove them. Removal/uninstall drops the old outer store and a
later same-id declaration receives a fresh namespace uid. Disable blocks
operations but does not erase. There is no public kernel storage-admin
endpoint: Settings shows declared ceilings, toggle, and bounded generic
outcomes, while live logical usage is available only through the app-scoped
`usage()` leaf. See [App-Isolated Stable Store
V1](./app-isolated-stable-store.md).

`backend/vetkeys/` separates immutable namespace encoding, stable registry
operations, management-canister adaptation, and lifecycle/derive policy. Slot
state stores no raw derived private key: only the random namespace nonce,
lifecycle manager (`key_holder`), status/generations, cached public key and
fingerprint, bounded counters, approximate charged cycles, tombstones, and
coarse audit entries persist. The namespace nonce is not returned to apps or
audit; the kernel-computed `derivation_input` is separate public encryption
material returned on demand. The
adapter alone selects `bls12_381_g2`, environment key name, `canister_id =
null` for public-key lookup, attached cycles, and fixed result sizes. Raw
management rejects are collapsed to closed errors.

Reservation and public-key acquisition revalidate declarations after awaits.
Derivation additionally validates the currently authorized principal and the
never-reused slot uid supplied by the trusted browser broker, generation,
status, concurrency, cycle floor, namespace inputs, and environment
before and after management calls. The `key_holder` controls lifecycle only;
all currently authorized Neutron principals may derive enabled retained
generations. Derivation has no time-window request limit; bounded pending and
concurrent work, attached-cycle bounds, and the low-cycle reserve remain. The
slot-nonce `raw_rand` dispatch and each uncached public-key management lookup
contribute the fixed 260,000-cycle call base even though they attach no cycles;
a cached lookup contributes none. The
install service invokes vetKeys configuration cleanup only at
journal commit: manifest removal suspends retained slots, uninstall retires
them, and abort preserves them. See
[App-Isolated vetKeys](./app-isolated-vetkeys.md).

### Authorization Storage And The Single Owner

The Neutron product model allows exactly one human owner per canister. It does
not support multiple users, roles, teams, or per-user kernel state. That owner
may authorize multiple principals as equivalent owner credentials, including a
recovery identity or trusted CLI tool. Provisioning also needs technical
bootstrap authority, and the canister acts as its own installer/controller.

Authorization is a flat set of principals in `mem.core.authorized`.

`main.mo` provides:

- `kernel_authorized_add(id)` to add a principal.
- `kernel_authorized_rem(id, caller)` to remove a principal other than the
  active caller.
- `kernel_authorized_recover(id, caller)` to let a verified IC controller
  restore kernel authorization without already having kernel authorization.
- `kernel_activation(request, caller)` to arm or consume one dispenser
  ownership handoff.
- `is_authorized(id)` as an internal check.
- `kernel_check_authorized((), caller)` as a public query check for the caller.
- `kernel_access_snapshot((), self)` to return authorized principals and the
  current IC controller list.
- `kernel_controller_add(id, self)` and `kernel_controller_rem(id, self)` to
  update the canister's controller list through `aaaaa-aa`.

The auth checks are applied by `_neutron.mo`, not by most functions in `main.mo`.
The generator inserts:

```motoko
assert(NeutronKernel.is_authorized(NeutronCaller));
```

for every generated ordinary-app query/update method. An opted-in
`public_ingress_cycles` handler has no such ordinary wrapper and is reachable
only through its paid dispatcher. Only the reviewed kernel manifest may set
`"allow": "unauthorized"`; ordinary app validation rejects it and requires
`capabilities.public_ingress`.

The generated actor also calls:

```motoko
NeutronKernel.kernel_authorized_add(NeutronInstaller);
```

at actor initialization, where `NeutronInstaller` is captured from the actor class
caller. That seeds the initial authorized principal outside the generated public
method wrapper. During `post_upgrade`, Motoko supplies anonymous as this
constructor caller. `kernel_authorized_add` therefore ignores and removes the
anonymous principal before doing any add; this also scrubs state written by
older actor versions that accepted it.

Consequently, the set may include installer principals as well as the human
owner's browser, recovery, and tool principals. A dispenser installer is
present only during bootstrap: successful activation `#set` removes it before
the final ownership link is exposed. The set is an authority list, not a user
list. Every retained entry receives the same full kernel authority and must be
trusted accordingly.

`settings/Access.mo` uses the synchronous replicated
`Principal.isController(caller)` system check for controller-only recovery and
activation. Operations that need the full controller list load it lazily with
`canister_status` and send a full preserved list to `update_settings`. It rejects the anonymous
principal, enforces the IC limit of 10 controllers, serializes controller
mutations initiated through the kernel, and refuses to remove the Neutron
canister's own principal. Keeping self as a controller is required for later
self-upgrades and for this settings surface to make further controller changes.
Controller mutations omit the optional `sender_canister_version` guard. The
controller list is loaded through an awaited `canister_status` call, and its
response callback advances the caller's canister version before the subsequent
`update_settings` request is processed. Binding that request to the earlier
version would make an otherwise valid controller change reject itself.
The public wrappers still require kernel authorization before any access or
controller method runs. `kernel_authorized_recover` and `kernel_activation` are
narrow exceptions. Recovery accepts an unauthorized caller, then grants access
only if that actual caller is currently an IC controller. Activation
`#set(hash)` performs the same controller verification, while `#use(code)`
derives the new authorized principal from the actual non-anonymous caller and
accepts it only when its SHA-256 value matches the single stored hash. The
successful use has no `await`, so adding authority and deleting activation
state are atomic. A controller may recover an arbitrary owner/tool principal
because it already has the stronger ability to replace the canister code;
activation never accepts an arbitrary target principal.

Currently reviewed kernel methods whose generated wrappers permit an
unauthorized caller are:

- `kernel_authorized_recover` (the backend then verifies the actual caller with
  `Principal.isController`)
- `kernel_activation` (the backend verifies controller authority for `#set` or
  a one-time bearer and actual caller for `#use`)
- `kernel_check_authorized`
- `http_request`
- `http_request_update`

`http_request` receives only its Candid request. Caller/self injection is not
part of the public HTTP wrapper.

The assembler-generated `kernel_runtime_info` query is not a manifest method,
but it performs the same `NeutronKernel.is_authorized(NeutronCaller)` check before
returning deployment, app, or memory inventory.

### Static Asset Storage

Static asset mutation is exposed through `kernel_static(cmd)`.

`StaticCmd` variants:

- `#store { key; val }`
- `#store_chunk { key; chunk_id; content }`
- `#delete { key }`
- `#clear { prefix }`

`File` values passed to `#store` contain the first content blob, content encoding,
content type, and total chunk count. The backend asserts `chunks > 0`.

The storage flow is:

1. `#store` calls `cert.chunkedStart(key, val.chunks, val.content, callback)`.
2. When the certified HTTP helper has all chunks, the callback inserts an
   `Assets.Doc` into the Core asset map with the full `[Blob]` chunk array.
3. `#store_chunk` calls `cert.chunkedSend(key, chunk_id, content)`.
4. `#delete` removes the primary-key entry and deletes certification state.
5. `#clear` iterates matching map keys, deletes each asset, and deletes its
   certification state.

`kernel_static_query({ #list = { prefix } })` returns up to 20,000 keys matching
the same prefix range and is authorization-protected by the generated actor. It
requests one extra key internally and traps instead of silently returning a
partial list when that bound is exceeded.

`kernel_static_query` only lists keys; clients fetch bodies through IC HTTP
response certification version 2. Compiler clients list `/mo/`, while the
trusted frontend may list one ordinary app subtree for artifact inspection.
The inspection tools compose these existing operations in the frontend and add
no backend method, managed-memory schema, or upgrade hook. Kernel root inventory
details are in [Asset Storage And HTTP Serving](./asset-storage-and-http-serving.md).

`apps/kernel/src/tools/install.ts` is the main upload client:

- `prepare_files` rewrites package paths.
- `web/*` becomes the selected app web prefix.
- `mo/*` is hash-checked and moved under the Motoko module prefix.
- Other files go under `<app_prefix>pkg/`.
- `upload_files` uploads files with at most 10 concurrent file tasks.
- Files are split into 1 MiB chunks.
- Non-image files are gzipped; image files use `identity` encoding.
- The asset key is `"/" + path`, except `index.html` maps to `/`.
- The first chunk is sent with `#store`; later chunks are sent sequentially with
  `#store_chunk`.

The install reducer prepares `/system/apps.json`, uploads package files, stores
the current Candid at `/pkg/neutron.did`, and, for a record-capable operation,
stages the exact pre-dispatch build record at
`/system/deployment-build-record.json` before calling the inline or chunked
install-code path.

### Certified HTTP

`apps/kernel/backend/certified_http.mo` owns static response certification, and
`apps/kernel/backend/certified_http_v2.mo` owns the closed response profiles for
app-scoped certified assets. They share one certified root but keep separate
storage, route, and streaming authority. The emitted IC HTTP response
certification protocol remains version 2 and is independent of both
`certified_assets.api: 2` and authored `http_routes.api: 1`. Exact version
negotiation, request expressions, Host/origin rules, routing priority, success
and absence proofs, caching, initialization, and qualification status have one
canonical contract:
[Certified HTTP And Certified Assets](./kernel-http-v2-and-certified-assets.md).

`http_request_update` is the unauthorized gateway update entrypoint. It
independently repeats all preflight and authority checks, persists admission,
then awaits only a compiler-owned self-call wrapper. POST replies use update
consensus rather than a certified query proof when the gateway follows the
honest upgrade. Query preflight only selects that upgrade path; it neither
executes app code nor returns app output.

Static assets may use the kernel-owned streaming callback. Synthesized
certified-asset read routes never do and never fall through to the static asset
lookup. Committed
package/compiler metadata remains public integrity-protected data, while
non-allowlisted `/system/**` state remains HTTP-internal. Qualification remains
the status recorded in the canonical certified-assets document.

The same static HTTP service owns ordinary browser-surface origins. The
assembler configures the exact adopted app set and one derived hostname per
tile ID, tray, and ordinary background. Certification binds an installation
document to the matching app subtree, exact Host, `Sec-Fetch-Dest: iframe`, CSP,
Permissions Policy, and Kernel-only `frame-ancestors`; subresources have a
separate MIME/destination allowlist. Installation hosts cannot execute Kernel,
other-app, package-metadata, top-level-document, or unwanted worker responses.
Camera and microphone are only the response-policy ceiling: the frontend still
must delegate an exact declared tile through its iframe `allow` attribute, and
media never enters this backend.

### Management Canister Self-Upgrade

`main.mo` uses the focused management-canister interface in
`aaa_interface.mo`, including `install_code` and the settings/status methods
used by trusted kernel services.

Small actors use `kernel_install_code(inp, self)`:

- Requires authorization through the generated wrapper.
- Receives `{ wasm : [Nat8]; candid : Text; deployment_id : Text }` and requires
  a matching stable install journal.
- Calls management canister `install_code`.
- Uses `mode = #upgrade`.
- Uses `arg = []`.
- Uses `wasm_module = inp.wasm`.
- Uses `canister_id = Principal.fromActor(self)`.
- Sends the current `Prim.canisterVersion()` as `sender_canister_version` so the
  request is bound to the actor version that creates it. This is not a
  cancellation mechanism: a request already accepted into the management
  queue remains valid after later ordinary updates.

Actors whose compressed install request would exceed the 2 MiB ingress ceiling
use the same journal through three additional authorized methods:

- `kernel_install_wasm_chunks_clear` clears only this canister's management
  chunk store. If activation was already dispatched in the predecessor actor,
  it first uses a FIFO `canister_status` fence.
- `kernel_install_wasm_chunk` accepts one nonempty chunk of at most 1 MiB,
  requires a 32-byte expected SHA-256, requires the exact pending
  undispatched journal before and after the awaited management upload, and
  rejects a different returned hash.
- `kernel_install_code_chunked` accepts 1–100 32-byte chunk hashes and one
  32-byte module hash, records the same dispatch marker, and sends the
  management canister's `install_chunked_code` as a one-way self-upgrade with
  the same upgrade mode, memory persistence, empty argument, and sender-version
  binding as the inline route.

The frontend clears before upload and again after observing the target actor,
before journal commit. Recovery also clears before committing. A failed
predecessor activation clears through the management fence before the journal
is aborted. Chunk upload is not a general management-canister capability and
is not exposed to apps.

The backend does not use `inp.candid` in the management call. Candid, stable
signature, registry, manifests, and web assets remain staged until runtime
verification succeeds.

The management canister call is written as a one-way call in `main.mo`; the
frontend comment in `apps/kernel/src/reducer/apps.ts` says the wasm install call
returns immediately because the management canister call is one-shot.

For this to work operationally, the Neutron canister must be able to upgrade
itself. `neutron-provision` ensures that a freshly installed or reinstalled
Neutron canister is one of its own controllers before completing deployment.

### Install Journal And Activation

`mem.install` stores at most one pending journal. The backend exposes
`kernel_install_begin_checked`, `kernel_install_status`,
`kernel_install_commit`, and `kernel_install_abort`. A journal contains a
bounded deployment id, staged asset copies, app-prefix clears, removed app ids,
and complete committed/target app-instance inventories with kernel-assigned
installation identities and capability-plan fingerprints.

The client uploads content-addressed `/mo` files early, stages every mutable
asset under `/system/staging/<deployment-id>/`, including the canonical
deployment build record when supplied, records the journal, and sends the
one-way upgrade. It also stages a bounded cleanup list containing only
modules from the authenticated pre-install baseline that are absent from the
compiled reachable-module set. The kernel writes a protected dispatch marker
atomically with the upgrade send. It polls generated `kernel_runtime_info`; an
atomic backend check permits only the expected running deployment to commit.
The predecessor actor remains live until activation. An activated target actor
keeps every non-kernel app scope inactive until commit, including scopes whose
version and capability plan appear unchanged; those facts cannot prove that
package code or public ingress is unchanged, including during an explicitly
allowed trusted-local same-version development redeploy.
Commit clears replaced app prefixes, copies and certifies staged assets,
promotes the target inventory, reconciles backend calls, Connections, vetKeys,
public-ingress routes, certified route records/proofs, and generic runtime resources, then invokes the
compiler-generated managed-memory callback. That
callback clears only optional retirement roots staged by this deployment and
asserts the exact deployment id. Module cleanup and journal/staging removal
follow; scheduler reconciliation completes in the same outer update. Any trap
rolls back the whole Motoko message, including stable-memory clears, metadata,
and resource cleanup. The next successful upgrade asserts every recorded
retired optional is null before omitting it from the stable shape.

Abort is immediate before dispatch. After dispatch, it first awaits a
successful self `canister_status` call as a FIFO management-queue fence, then
rechecks the journal and running deployment. If activation succeeded the new
actor rejects abort; if the queued install was terminally rejected the old
actor can safely clear it. Ambiguous fence failures retain the journal and
marker. Generic static commands cannot overwrite or delete the marker.

### Local Settings Snapshot

The kernel exposes `kernel_settings_snapshot(null)` as an authenticated,
synchronous query. `backend/settings/Service.mo` keeps the runtime primitives
isolated from normal app code and returns a versioned record containing:

- the current balance from `mo:core/Cycles.balance()`;
- RTS version, Wasm memory, current heap, total allocation, reclaimed bytes,
  and maximum live heap from `mo:prim`;
- physical and logical stable-memory sizes converted from 64 KiB pages to
  explicit byte fields.

The snapshot has no persistent state and does not change any managed memory
schema. The values describe the whole Motoko runtime at one instant; they are
not accounting guarantees or per-app attribution. The browser uses this local
kernel query whether or not its principal is also an IC controller. The
optional access snapshot separately makes an asynchronous `canister_status`
request for controller data without replacing the local metrics query.

Per-app attribution is a separate authenticated query,
`kernel_app_usage_snapshot(null)`. It returns snapshot version 2, the
current UTC day number, and active exact-installation rows containing sparse
daily buckets and 30-day/lifetime totals. Instructions and measured executions
are saturating `Nat64`; outgoing cycles containing fixed authorized-ingress and
broker/timer/handler call bases plus net explicit transfers, and accepted
incoming public-update cycles, are exact unbounded `Nat`. It contains no
caller ids, destinations, inputs, outputs, error text, or per-request log.

## Inferred Design Intent

The code appears to treat the kernel backend as an app module that is assembled
into a larger generated actor with other installed apps. The kernel keeps its
state in a named memory record, while `_neutron.mo` owns actor-level concerns:
persistent memory version wrappers, Candid exposure, auth assertions, query/update
mode, caller/self argument injection, and the initial authorized installer.

The asset system makes all kernel and installed-app frontend
files certified static assets in the same canister that runs the backend. The
frontend install path uses a stable journal so active metadata always describes
the actor that is actually running.

## Open Questions And Gaps

- `kernel_install_code` accepts `candid` but ignores it. The current frontend
  writes `/pkg/neutron.did`; the backend does not verify that asset against the
  wasm or use it as install metadata.
- Authorization is a single mutable set and has no roles. vetKeys maintains a
  capability-specific bounded lifecycle/derive audit, but there is no general
  backend authorization audit covering every kernel operation.
- Static `http_request` lookup serves only exact canonical asset keys, and
  route lookup serves only exact stored suffixes beneath a declared mount.
  There is no directory-to-`index.html` fallback.
